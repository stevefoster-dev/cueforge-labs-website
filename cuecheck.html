02

The rules, before the panic

Decide how content is named while nobody is shouting

Naming, versioning and slot ownership are settled as project rules, and the application shows you the exact result of those rules before a single file arrives.

Job — keep names honest

One convention, stated once, applied to everything

A project sets its file prefix and its versioning mode, and every delivery in that project inherits them. Consistent naming is what makes the rest of the pipeline — and the console — predictable.

  • Automatic renaming to the show's convention with prefix enforcement
  • Sequential or date-based versioning, chosen per project
  • Deliverable identifiers that drive routing and visibility
  • Slot ranges, show order and reservations so a slot can be claimed before content arrives

Boundary CueCheck validates and delivers. It does not transcode content into spec on your behalf.

Job — catch it early

Simulate the delivery before anything moves

Paste a filename a vendor is about to send and the preview shows exactly where it would land under the current rules. Nothing is copied, renamed or moved to answer the question.

  • Live preview of the at-rest path produced by the current rules
  • Simulation from an arbitrary pasted filename, with no files moved
  • Probe-driven checks on resolution, codec, frame rate, colour and file size
  • Rejected and needs-review files are separated rather than silently dropped

Boundary CueCheck is a production-network tool, not a public content-distribution service, and it does not play back or drive a show.

03

The safe loop

Validate first, deliver second, swap only when complete

Content that fails the spec never reaches a playback machine, and a destination is only updated once the whole target set is ready — so a half-finished delivery cannot become a half-finished show.

  1. 01

    Watch

    Monitor the delivery folder the content team is already using, without changing how they work.

  2. 02

    Validate

    Probe each file against the spec profile for its destination, and state the reason in plain language when it fails.

  3. 03

    Name and stage

    Apply the show's naming convention and hold the file in a controlled staging area.

  4. 04

    Deliver

    Push to the required destinations over the local network and record what actually landed.

  5. 05

    Swap and report

    Complete the target set, swap atomically, and tell the room what changed.

Built for

  • Video engineers and media server operators receiving content under time pressure
  • Content leads enforcing one spec across several creators
  • Production managers who need delivery status without asking for it
  • Shops running the same validation rules across repeat shows

Outside its authority

  • It validates and delivers — it does not play back or drive a show
  • It does not transcode content into spec on your behalf
  • It does not manage a media server's internal show state
  • It is a production-network tool, not a public content-distribution service
